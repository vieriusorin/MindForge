# One server-only secret key, for the group heatmap's cross-member read

Decided 2026-11-04 by the user (MF-0011, concern C-2). The group heatmap needs every member's attempts so the TS engine can replay each member's memory (FSRS lives in `src/engine/memory`, not in SQL). Any database function a signed-in member can call would hand them the other members' raw attempts through the Data API, which D-4 forbids. So the read, `public.group_attempts`, is executable by `service_role` only. The app calls it with `SUPABASE_SECRET_KEY` from one server-only file, `src/server/groups/get-group-heatmap.ts`, through `src/server/supabase/secret.ts`, and only the per-region aggregate leaves the server. We rejected re-implementing FSRS in SQL, because it would mean two copies of the formula that can drift apart.

This supersedes MF-0004 SC-8 ("no service-role or secret key in the app or in Vercel env") for this one key. Vercel env now holds four variables. The heatmap shows only when 3 members other than the viewer have played, and never shows a member count (MF-0011 C-3).

**Consequences:** the secret key bypasses RLS. Least privilege therefore rests on code, which a test locks (`src/server/supabase/__tests__/secret-client-importers.test.ts`): exactly one importer, the key named in `secret.ts` only, and never a `NEXT_PUBLIC_` variable. A second use of the key needs a new ADR, not an edit to that test. The definer function still refuses a viewer who isn't a member of the group. It trusts the viewer id it is given, though, so the page must pass the id from the verified session (`getCurrentUser`). A page bug that passed another member's id would not be caught, but it would still yield only that group's aggregate. The key must be rotated if it is ever exposed (Supabase dashboard → API keys).
