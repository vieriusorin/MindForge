## FIX details

### D2.S1.q1: option A rationale
- **Problem:** "That wrapper shape comes from other vendors' function-calling APIs" is outside knowledge. The cited define-tools page never mentions other vendors.
- **Page:** "A user-defined tool definition includes: `name` ... `description` ... `input_schema` ... `input_examples` (Optional)".
- **Replace the A rationale with:** "A Claude user-defined tool has no `function` wrapper or `parameters` field: it takes `name`, `description` and `input_schema` directly."

### D2.S1.q3: option C rationale
- **Problem:** "it can only make wrong picks more frequent" is an unsupported causal claim. The page's guidance for selection ambiguity is consolidation and namespacing. (Also, on Opus 5.5 and the other listed models, `any` returns a 400 error anyway.)
- **Page:** "Fewer, more capable tools reduce selection ambiguity" and "prefix names with the service ... This makes tool selection unambiguous".
- **Replace the C rationale with:** "Forcing some tool call does not help Claude tell which tool fits; the documented fix for selection ambiguity is consolidating related operations and namespacing tool names by service."

### D2.S2.q2: option C rationale
- **Problem:** the item cites the overview page, but "Claude handles server-tool errors transparently" and "report client-tool errors with `is_error`" appear only on handle-tool-calls. The overview never mentions `is_error`.
- **Overview page:** "Client tools ... Your code runs the operation and sends back a `tool_result`. Server tools ... run on Anthropic's infrastructure: you see the results directly without handling execution".
- **Replace the C rationale with:** "It is the reverse: you see server-tool results directly without handling execution, while for client tools your code runs the operation and sends back the `tool_result`." Alternatively, change `source.url` to handle-tool-calls and keep the current text, since that page says: "Unlike client tools, you do not need to handle `is_error` results for server tools."

### D2.S3.q3: key text and rationales not on the cited page
- **Problem:** the item cites the architecture page. That page has no "URI", "MIME", "passive" or "read-only", and never says prompts are user-invoked or user-controlled. Those details are on server-concepts, which in turn does not cover elicitation (option D). The page that supports the key is architecture: "It can expose tools for querying the database, a resource that contains the schema of the database, and a prompt that includes few-shot examples".
- **Fix (keep the architecture source):**
  - B text: "A resource that contains the schema, which the application retrieves and passes to the model as context."
  - B rationale: "Resources are data sources that provide contextual information to AI applications; MCP's own database example exposes the schema as a resource and querying as tools."
  - C rationale: "Prompts are reusable templates that help structure interactions with the model, not a channel for serving data."
  - A rationale (tighten): "Tools are executable functions for performing actions; read-only context such as a schema fits a resource."
  - D: unchanged. Architecture supports it: "Elicitation: Allows servers to request additional information from users."

### D2.S1.card-tool-description
- **Problem 1:** "it decides whether and how to call a tool almost entirely from the description" overclaims. The overview says the decision rests on the request and the description, and the input schema governs how the input is shaped.
  - Overview: "Claude determines when to call a tool based on the user's request and the tool's description."
  - define-tools: "This is by far the most important factor in tool performance."
- **Problem 2:** whereItBreaks[2] calls the schema "a hard contract on the input's shape" before it mentions `strict`. Without `strict`, the schema is not guaranteed. The page ties the guarantee to strict: "Set `strict: true` on your tool definitions to enable schema validation."
- **Replace `simply` sentence 2 with:** "Claude never sees your code; it decides whether and when to call a tool from the user's request and the tool's description, and the description is by far the most important factor in tool performance."
- **Replace whereItBreaks[2] with:** "The schema is not a dance: it defines the input's shape, and with `strict: true` the inputs are guaranteed to match it exactly."

### D2.S3.card-mcp: whereItBreaks[0]
- **Problem:** "An MCP server only acts when a client calls it" is false per the cited page. Servers push notifications on their own initiative, and they can elicit input from users.
- **Page:** "Event-Driven: The server decides when to send notifications based on internal state changes" and "Elicitation: Allows servers to request additional information from users."
- **Replace with:** "The fungus trades on its own initiative. An MCP server mostly answers client requests; even its change notifications go only to clients that opened a `subscriptions/listen` stream asking for them."

### D2.S1.diagram-tool-choice
- **Problem 1 (branch coverage):** `CHOICE → MUST [any / tool]` reads as "any/tool always forces a call". The page documents that forced tool use fails on some models and with manual extended thinking. A decision node must cover that case.
  - Page: "Not every model and setting supports forced tool use. Where it isn't supported, `tool_choice: {"type": "any"}` and `tool_choice: {"type": "tool", ...}` fail".
- **Problem 2:** the label on `AUTO → NONE`, "answer already known", is imprecise. The overview says Claude "responds directly for stable knowledge, creative tasks, and conversational turns", and calls a tool when "the answer isn't already in context".
- **Suggested change:**
  - Relabel `CHOICE → MUST` as "any / tool (where supported)".
  - Add node `ERR`: "400 error: use auto + strict: true, or structured outputs".
  - Add edge `CHOICE → ERR`, labelled "any / tool where unsupported (some models, manual extended thinking)". Keep this generic so it doesn't date.
  - Relabel `AUTO → NONE` as "stable knowledge, creative or conversational turn, or answer in context".
  - Relabel `AUTO → CALL` as "request maps to a tool's described capability".

### D2.S2.diagram-loop
- **Problem:** `STOP → DONE [no (end_turn)]` has two issues.
  - `end_turn` appears on neither cited page (overview, handle-tool-calls).
  - The "no" branch asserts that every other stop reason is a final answer. The cited overview links "Stop reasons and fallback" for cases such as a pending server tool, so stopping without `tool_use` is not always a final answer.
  - Overview: "Claude reads the result and either calls another tool or answers" (that is the card's wording). The page itself says: "Claude responds with `stop_reason: "tool_use"` and one or more `tool_use` blocks."
- **Suggested change:**
  - Relabel the edge as "no".
  - Relabel `DONE` as "Claude answers in text (check stop_reason before treating it as final)".
  - Or, if a second branch is wanted, add a node "Other stop reason: handle per Stop reasons and fallback".

## NOTE details

- **D2.S1.q5:** the key and the rationale for A name four specific models. The page's table will change as models ship. Re-verify this item whenever the define-tools page changes, or reword the stem to "On a model that rejects forced tool use (see the define-tools table)".
- **D2.S2.q6:** the B rationale says "the API then runs the pending server tool and the next response starts with its result". The page qualifies this: "for a server tool Claude called directly, the API runs it on that request and the next response starts with its result block". Suggested rationale: "Reply with only the client tools' `tool_result` blocks and keep the same `tools`; for a server tool Claude called directly, the API runs it on that request and the next response starts with its result block."
- **D2.S3.q6:** the key is correct for protocol version 2026-07-28, the version shown on the cached page. The page also says notifications are "Best Effort ... Clients should also rely on polling to preserve freshness of results." Consider adding to the B rationale: "Notifications are best effort, so a client should also poll `tools/list`." These method names are version-specific, so re-verify on each protocol revision.
- **D2.S3.diagram-mcp-participants:** every edge is true per the architecture and server-concepts pages. The asymmetry (LOCAL → TOOLS only) could still teach that local servers expose only tools. Either add LOCAL → RES and LOCAL → PROMPTS, or add a footnote that any server can expose all three. The diagram has no decision nodes.
