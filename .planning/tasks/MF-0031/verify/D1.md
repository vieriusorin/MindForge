## FIX details

### prod-prompting.D1.S3.q6 (option D rationale; drafter-flagged)

**Problem.** The rationale says "the docs make no casing guarantee for patterns either." The cited page
says nothing of the kind: the casing caveat is scoped explicitly to string `enum` and `const`
values. Patterns are listed only under "Pattern support (regex)" with no casing caveat. So the
rationale is unsupported, and because the page limits the caveat to enum/const, a learner could
defend D ("a `pattern` is compiled into the grammar, so exact case is enforced"). Two defensible
answers is a broken item.

**Passage.** "Structured outputs don't guarantee the capitalization of string `enum` and `const`
values … This applies to both JSON outputs and strict tool use. Compare enum values
case-insensitively, and avoid enum values that differ only in capitalization."

**Suggested replacement for option D** (clearly wrong per the page, same lure):
- text: "Switch from JSON outputs to strict tool use (strict: true), which matches enum values exactly."
- rationale: "The docs say the capitalization caveat applies to both JSON outputs and strict tool use; the documented remedy is case-insensitive comparison."

(If D must stay as is, the rationale should become: "The documented remedy is case-insensitive
comparison and avoiding values that differ only in case; the docs do not offer a pattern as the fix,
and complex patterns can return 400 errors." But D would remain arguably defensible, so prefer the
replacement.)

### prod-prompting.D1.S2.card-foraging-range (whereItBreaks #3; drafter-flagged area)

**Problem.** The card says "Higher effort does not reliably make visible answers longer on every
model (Claude Opus 5)". The source makes a different, model-scoped claim in the other direction:
on Claude Opus 5, *changing* (in practice lowering) effort does not reliably *shorten* responses,
because effort controls thinking volume, not visible length. "On every model (Claude Opus 5)" is
self-contradictory.

**Passage.** "Effort controls thinking volume, not visible response length: on Claude Opus 5,
changing effort does not reliably shorten responses, so prompt for length instead."

**Suggested replacement:** "On some models (for example Claude Opus 5) effort controls thinking
volume, not visible length: lowering it does not reliably shorten answers, so ask for the length
you want in the prompt."

Also (minor, same card):
- `simply` lists five levels as if universal; the page says "Not every model that supports `max`
  supports `xhigh`." Suggest appending: "(not every model supports every level)". NOTE: the
  level list will date.
- `contrast` claims "Few-shot examples steer the shape of the answer, not its cost", which the
  cited effort page does not cover. Either add the best-practices URL to `sources` or drop the
  sentence.

### prod-prompting.D1.S3.card-honeycomb (`simply`)

**Problem.** "Your code can parse it without try/catch-and-retry" is false standalone: the page
lists cases where the output may not match the schema and tells you to retry (max_tokens) or handle
a refusal. A truncated response will fail `JSON.parse`.

**Passage.** "Although structured outputs guarantee schema compliance in most cases, there are
scenarios where the output might not match your schema: … `stop_reason: "refusal"` … `stop_reason:
"max_tokens"` … The output might be incomplete and not match your schema. Retry with a higher
`max_tokens` value."

**Suggested replacement sentence:** "You no longer retry for schema violations, but your code
should still check stop_reason for a refusal or a max_tokens cut-off before parsing."

### prod-prompting.D1.S2.diagram-choose-effort (drafter-flagged)

**Problem 1: HI node.** "Long-running agentic or coding work? yes → xhigh or high, per the model's
recommendation." Several models' recommendations for agentic/coding work are `medium`, so the label
is wrong for them even with the hedge:
- Sonnet 5.5: "For agentic coding and multistep tool use, start with `medium` for well-specified tasks and move to `high` for harder or longer ones."
- Haiku 5.5: "**Start with `medium`** for most work, including agentic coding."
- Sonnet 4.6: "Medium effort (recommended default): … Suitable for agentic coding".
Only Opus 4.7/4.8 say "Start with `xhigh` for coding and agentic use cases"; the table's `xhigh`
row is for "Long-running agentic and coding tasks (over 30 minutes) with token budgets in the millions".

**Suggested HI label:** "The model's recommended level for agentic work (xhigh on Opus 4.7/4.8; medium or high on Sonnet 5.5 and Haiku 5.5)". Or, dating less: "Start at the model's recommended level for agentic and coding work".

**Problem 2: the "no: raise effort" loop.** Q3 "no" goes to the HI node from every path, so a
`low` workload that fails jumps straight to xhigh/high (skipping medium), and a workload already at
HI loops to itself. The page's advice is stepwise ("step down to `medium` or `low` … once your evals
show quality holds"; Opus 4.7: "up to `max` only when your evals show measurable headroom at `xhigh`").

**Suggested fix:** add node `UP` "Raise effort one level" and replace edge `Q3 → HI` with
`Q3 → UP` (label "no") and `UP → EV`.

**Minor:** Q1 groups "latency-sensitive" with `low`; the per-model text says "For chat and other
latency-sensitive work, start with `medium` or `low`" (Sonnet 5.5). LOW's "(subagents,
classification)": the table names only subagents; "classification" comes from the Haiku 5.5 model
headline, not a `low` recommendation. Suggest "(subagents, simple high-volume requests)" (Haiku 5.5:
"Use `low` … for chat, short tool tasks, and simple, high-volume requests").

NOTE: DEF label "(high; medium on Opus 5.5 and Haiku 5.5)" is correct today but is a per-model
default that will date.

### prod-prompting.D1.S3.diagram-criteria-to-ship (decision Q1)

**Problem.** "Is the answer categorical? yes → code-based grading; no → LLM grader" reads as
"non-categorical answers need an LLM grader". The page grades non-categorical outputs with code too
(ROUGE-L for summaries, cosine similarity for consistency, string match `key_phrase in output`)
and tells you to pick the fastest, most reliable method. The branch should ask whether a rule can
check it.

**Passage.** "choose the fastest, most reliable, most scalable method: 1. Code-based grading …
Exact match: `output == golden_answer` · String match: `key_phrase in output` … 3. LLM-based
grading: Fast and flexible, scalable and suitable for complex judgment."

**Suggested fix:** Q1 label "Can code check it (exact match, string match, a metric)?";
CODE label "Code-based grading (exact match, string match, ROUGE-L…)"; LLM label "LLM grader with a
clear rubric (complex judgment)". Edges unchanged.
