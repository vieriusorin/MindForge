## FIX details

### D3.S1.card-workflows-vs-agents

**Problem 1 (`inNature`):** It opens with "A river and a fox", but every sentence after that is about a canal
("Water in a canal goes exactly where the engineer dug it"). A river is not engineered, so the opening
contradicts the point of the analogy, which is a path fixed by code.

**Problem 2 (`whereItBreaks[1]`):** "A canal never improves by itself, while a workflow can still contain LLM
calls that make judgements inside each fixed step." "Improves" and "makes judgements" are different ideas,
so the line does not name a clear difference. The real difference is that each step of a workflow is an LLM
call. Page: "Workflows are systems where LLMs and tools are orchestrated through predefined code paths."

**Suggested replacement:**
- `inNature`: "A canal and a fox. Water in a canal goes exactly where the engineer dug it: predictable, cheap,
  repeatable. A fox hunting decides each move from what it smells and sees right now, so it can catch prey
  nobody planned for, but it burns more energy and sometimes runs the wrong way."
- `whereItBreaks[1]`: "Canal water makes no choices, while every step of a workflow is still an LLM call that
  reads, judges and writes; only the order of the steps is fixed by code."

### D3.S1.diagram-which-pattern

**Problem 1:** The edge `Path --"no: steps unpredictable"--> Agent` leads to the node "Agent or
orchestrator-workers". Read together with the "yes: workflow" label on the other branch, this says
orchestrator-workers is not a workflow. The page lists it under "Workflow: Orchestrator-workers". It is a
workflow whose *subtasks* are dynamic, while the orchestrate → delegate → synthesize structure stays fixed:
"a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results …
subtasks aren't pre-defined, but determined by the orchestrator."

**Problem 2:** The "What shape is the task?" decision covers three of the page's five workflows. It has no
branch for orchestrator-workers or for evaluator-optimizer ("particularly effective when we have clear
evaluation criteria, and when iterative refinement provides measurable value").

**Suggested replacement** (nodes and edges that change):
- Node `Path`: "Can your code fix the control flow ahead of time?" (decision)
- Node `Agent`: "Agent: the model picks its own steps in a loop, with stopping conditions"
- New node `Orch`: "Orchestrator-workers: a central LLM splits the task into subtasks it picks per input"
- New node `Eval`: "Evaluator-optimizer: generate, critique, refine in a loop"
- Edges: `Path → Shape` "yes: workflow"; `Path → Agent` "no: open-ended, steps unpredictable";
  `Shape → Orch` "subtasks vary per input"; `Shape → Eval` "clear evaluation criteria".
  Keep the existing `sequence`, `categories` and `independent` edges.

### D3.S2.q4

**Problem:** The stem says "A multi-turn agent resends the same long system prompt and tool list on every
call." In a multi-turn conversation the newest user message becomes unchanged history on the next turn. The
page states that a breakpoint on the final block works in that case. That makes distractor A ("On the newest
user message") defensible. Its rationale ("content that changes every request … never get a read") is
false for a growing conversation.

Page: "**Key takeaway:** … In a growing conversation the final block works as long as each turn adds fewer
than 20 blocks: earlier content never changes, so the next request's lookback finds the prior write. For a
prompt with a varying suffix (timestamps, per-request context, the incoming message), place the breakpoint at
the end of the static prefix, not on the varying block."

**Suggested replacement:**
- Stem: "A classification service sends the same long system prompt and tool list on every request, followed
  by a different incoming message each time. Where should the explicit cache breakpoint go so later requests
  read from the cache?"
- Option A text: "On the incoming message, because that block is always last in the request."
- Option A rationale: "The incoming message differs on every request, so the prefix hash at that breakpoint
  never matches; you pay for a fresh write each time and never get a read."

The rest of the item can stay as it is.

### D3.S3.q5 (drafter-flagged option D)

**Problem:** The text of distractor D, "acceleration limits, which never carry retry-after", makes a claim
the page does not support. The page says nothing about headers on acceleration-limit 429s. It says only
"Not every 429 carries it; the spend-cap 429 never does." Because the page does not say whether
acceleration 429s carry the header, a careful learner cannot rule D out on the "no retry-after" clue. Only
"for hours" separates D from the key, and the page does not say how long acceleration limits last either.

**Suggested replacement for D:** use a distractor that the page clearly rules out and that still works at
expert level:
- Text: "The organization reached a spend limit it set itself on the Billing page, below its tier's cap."
- Rationale: "A spend limit you set returns HTTP 400 invalid_request_error, not a 429; the 429 with no
  retry-after that keeps failing until access resumes is the tier's monthly spend cap."
- Supporting passage: "When usage reaches a spend limit you set, requests return HTTP 400 with error type
  `invalid_request_error`."

The key (C) and its rationale are correct ("the response has no `retry-after` header. Retrying, including
the SDK's automatic retries, fails until access resumes").

### D3.S3.card-token-bucket (drafter-flagged `contrast`)

**Problem:** The current text is "A 429 says you are over your own limits; a 529 overloaded_error says the
API is under high traffic across all users. Both are worth retrying with backoff, but only the 429 is fixed
by changing your own traffic." It has three faults:
1. "Both are worth retrying" is false for the spend-cap 429, which contradicts the card's own third
   `whereItBreaks`. Page: "Retrying, including the SDK's automatic retries, fails until access resumes."
2. "Only the 429 is fixed by changing your own traffic" is false for the spend-cap 429, which needs a higher
   tier or the start of a new month. It holds only for rate and acceleration limits.
3. "A 529 … says the API is under high traffic" overstates the page, which says the API "is temporarily
   overloaded" and that a 529 "**can** occur when the API experiences high traffic across all users."

**Suggested replacement `contrast`:** "A rate-limit 429 means your organization went over one of its own
limits: wait the retry-after seconds (the SDK honours it) and smooth your traffic. A 529 overloaded_error
means the API itself is temporarily overloaded, which can happen under high traffic across all users; the
SDK retries it with exponential backoff. The exception is the spend-cap 429: it has no retry-after, and
retries fail until access resumes."

Supporting passage: "The official SDK automatically retries transient failures (such as connection errors,
rate limits, and 5xx server errors) with exponential backoff, twice by default, honoring the `retry-after`
header when present."

### D3.S3.diagram-error-retry (drafter-flagged 500/529 node and 4xx code list)

**500/529 node (flag checked, OK):** "500 or 529: retry with exponential backoff" is supported. For 500 the
page says "Retry the request with exponential backoff". For 529, the page says the SDK retries "5xx server
errors with exponential backoff". The `Persist` "contact support with the request_id" edge is stated only for
500 ("if the error persists, contact support with the request ID"). That is acceptable, but the support step
is not documented for 529.

**Problem 1 (429 branch):** The edge `Header --no--> Cap` says "a 429 with no retry-after is the spend cap".
The page does not give that rule. It says "Not every 429 carries it; the spend-cap 429 never does", and it
names a different test: "On the Messages API, `error.details.error_code` is `enforced_spend_limit_reached`.
Use it to tell this response apart from a rate limit."

**Problem 2 (4xx code list):** 400, 401, 403, 404 and 413 are all correctly "fix it, don't just retry". The
status decision leaves cases out, though:
- 402 `billing_error` ("issue with your billing or payment information")
- 504 `timeout_error`, plus the 500 that carries `timeout_error` ("If the error type is `timeout_error`
  instead, see the 504 entry … use the streaming Messages API"). Under the current diagram, a timeout 500
  would be sent to "retry with backoff" when the page says to switch to streaming.
- 409 `conflict_error` ("Resolve the conflict, then retry the request") contradicts the `Fix` node's
  "retrying will not help", so leave 409 off that node, as the current diagram does, or give it its own
  node.

**Suggested replacement** (nodes and edges that change):
- `Fix`: "400, 401, 403, 404, 413: fix the request, key or permissions; retrying unchanged will not help"
- New `Billing`: "402 billing_error: fix payment details in the Console"
- `Header` → rename the question to "Is error.details.error_code enforced_spend_limit_reached?" (decision)
- `Cap`: "Spend cap: no retry-after, retries fail until access resumes or a higher tier is granted"
- `Wait`: "Rate or acceleration limit: wait retry-after seconds if given, then retry; ramp traffic gradually"
- New `Timeout`: "504 or timeout_error: use streaming for long requests"
- `Backoff`: "500 api_error or 529 overloaded_error: retry with exponential backoff"
- Edges: `Status → Billing` "402"; `Header → Cap` "yes"; `Header → Wait` "no";
  `Status → Timeout` "504 / timeout_error"; `Status → Backoff` "500, 529". Keep `Backoff → Persist`
  "persists".

## NOTE details

  the docs but absent from the cited context-engineering page. It is acceptable for a distractor. If
  everything must come from the page, use instead: "Context rot is about recall degrading as tokens grow,
  not about anything expiring."
- **D3.S2.q6:** The rationale for D ("max_tokens caps output") is not on the cited page. Suggested
  rationale: "A bigger single context still fills with every search result; the article isolates search
  context in sub-agents instead."
- **D3.S2.card-attention-budget:** In `whereItBreaks[2]`, the claim that context rot is something "you only
  see if you measure it" is not on either cited page. The page says only "a performance gradient rather than
  a hard cliff". Suggested text: "Shade is easy to see; context rot is a gradient rather than a hard cliff,
  so the model stays capable but quietly loses precision as context grows."
- **D3.S2.diagram-long-horizon:** The edge `Full --no--> JIT` reads as "just-in-time retrieval is for when the
  window is not full". On the page, JIT is a general retrieval strategy and is what keeps the window from
  filling. Suggested label: "no: keep loading just in time". The other edges match the page's "choice
  between these approaches depends on task characteristics" list (back-and-forth / milestones / parallel
  research).
- **D3.S3.q6 (drafter-flagged option D rationale):** "Sampling randomness is not a security control" is true
  but comes from outside knowledge, because the page never mentions temperature. The second clause is
  accurate. Suggested rationale: "No sampling setting appears among the page's mitigations; it relies on
  structure (tool results, JSON encoding), screening and least privilege."
