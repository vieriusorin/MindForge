## Findings

Verified against the live local stack (read-only): RLS on for all three tables; `authenticated` has table-level SELECT only, plus column UPDATE on `profiles.display_name` and `groups.name` (so `invite_code`, `created_by`, `pack_slug`, `role` and `user_id` cannot be written directly); `anon` has no table grants; every `private.*` function ACL is `{postgres, authenticated}` or `{postgres}` only; all functions are `search_path=''`; the `private` schema is not in `api.schemas`; `supabase db advisors --type security` reports "No issues found". Every SECURITY DEFINER op checks `auth.uid()` (`create_group`/`join_group` raise on null; `rotate_invite_code` raises unless `is_admin`). `safeNextPath` is applied on every `next` hop (sign-in page, sendMagicLink, callback). Server code uses `getClaims()` only, `getSession()` never. Per-user reads are uncached under `<Suspense>`, and there is no mutation on GET `/join/[code]`. No secret is in `src` outside the test harness, and no `NEXT_PUBLIC_` variable holds one. The frozen test hash matches FROZEN.json.

- [note] src/server/supabase/proxy-session.ts:49-52 — the optimistic redirect to `/sign-in` copies cookies from `response`, but not the `Cache-Control`/no-cache headers that `setAll` put on it (lines 29-30). When `getClaims()` clears a dead session on a `/groups*` request, the cookie-clearing redirect goes out without the no-store headers that @supabase/ssr asks for. It is low impact (a 307 to `/sign-in`), but it breaks the ssr rule. Copy the headers too.
- [note] src/server/http/request-origin.ts:7-15 — the origin comes from the client-controlled `Origin`/`X-Forwarded-Host`/`Host` headers and feeds `emailRedirectTo` (src/features/auth/actions.ts:27). Today the only guard against an attacker-chosen callback host in a victim's magic link is the Auth redirect allowlist (supabase/config.toml:165). Locally that is fine. For the hosted hand-off, keep `additional_redirect_urls` to exact production origins (no wildcard hosts), or build the URL from a configured site origin.
- [note] src/features/groups/actions.ts:67-73 — `rotateInviteCode` ignores the RPC error and does not validate `groupId`. A failed rotation (non-admin, network, DB) looks like success because the page just refreshes with the old link. It is not a security hole, since the DB refuses the call (verified, SC-4).
- [note] supabase/migrations/20261103064106_mf0002_groups.sql:99-120 — `create_group` validates `pack_slug` only by regex. A user calling the RPC directly with a well-formed but unknown slug gets a group whose page throws in `getPack` (src/app/groups/[groupId]/page.tsx:28). Only the caller is affected. Nothing caps how many groups one user can create, which is a spam vector on the hosted project.
- [note] supabase/migrations/20261103064106_mf0002_groups.sql:228 — this `revoke all … from anon, authenticated` is load-bearing. On this stack, the `postgres` default ACL for new tables in `public` grants `anon`/`authenticated` `Dxtm` (TRUNCATE, REFERENCES, TRIGGER, MAINTAIN), and TRUNCATE bypasses RLS. The three tables are clean. Every future migration that adds a table must repeat this revoke, so it is worth a comment or a check.
