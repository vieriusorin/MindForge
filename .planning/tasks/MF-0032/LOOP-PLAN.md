## Riskiest step

**Step 1, the definer function.** It runs as owner over every learner's attempts.
- Failure modes: a torn read (the hash checked against one version, the key read from another); an
  overload left behind (the old 2-arg function still callable without the check, or ambiguous PostgREST
  resolution); a grant missed on the new signature; the hash taken from the client instead of the registry.
- Proof: SC-7 lists the exact signatures and privileges. SC-2 runs an open sync transaction against a
  concurrent answer. SC-6 checks that the stored hash equals the REGISTRY hash, including on the 2-arg call
  where the client sent none. The MF-0005 gate catches anon EXECUTE.
- Versioned judgement (DESIGN rule): the attempt names the version read (`p_content_hash`) and is refused
  when it differs from the stored version. The app check (step 6) covers the opposite race.
- **UI bypass:** the server refuses whether or not the page is stale. A direct action call with an old hash
  → `checkQuestionAnswer` `changed`. A direct RPC with an old hash → 55000. A direct RPC with NULL → graded
  against the current key (no worse than today: the caller chooses their answer freely anyway; decided at
  DESIGN).
- **Re-runnable writer (sync), state it doesn't own:** (a) no ids or manifests on disk; (b) attempts and
  reviews by other actors are untouched (the sync never writes `attempts`; `items` delete cascades to
  reviews as today, unchanged); (c) failure order is unchanged: `validatePacks` runs for all packs before
  connecting; merging two transactions into one only removes the keys-committed/items-failed state. No new
  destructive write.

## Rejected options

- **Required `p_content_hash`.** It breaks the frozen MF-0003, MF-0016 and MF-0029 DB tests and the dev
  seed, and gains no security (see DESIGN).
- **Bind the key row itself (`question_keys.content_hash`).** It duplicates the registry hash (two owners
  of one fact). One sync transaction plus a one-statement join gives the same guarantee.
- **`FOR SHARE` lock on the items row.** It would serialise grading behind a running sync. A
  single-snapshot read is enough and never blocks a learner.
- **Pass hashes as a separate prop (`hashes: Record<id, hash>`) to avoid changing the DTO.** The duel
  fixture breaks anyway, and the hash would travel apart from the item it versions. The cuckoo precedent
  puts it on the DTO.
